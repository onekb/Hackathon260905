# 需求与决策记录

最后整理：2026-09-05，Asia/Shanghai。实现程度见 [进度](progress.md)，接口定义见 [架构与协议](architecture-and-protocol.md)。

## 目标与范围

让买家从独立卖家购买一次推理请求，并看清报价、预算、用量、费用和链上结算结果。黑客松优先展示 Web3 能直接约束的资金规则；用户在需求讨论开始时表示约有 8 小时开发窗口，这不是当前剩余时间。

| 范围 | 已采用要求 |
| --- | --- |
| 网络 | Monad 测试网，chain ID `10143` |
| 买家 | 在线体验台和最小 API 共用一个订单及结算流程 |
| 卖家 | 自行运行独立进程及本地控制台；模拟响应，不接真实模型或算力机房 |
| 连接 | 买家访问平台 API；卖家主动通过 WSS 接入 Router，无需公网地址 |
| 报价 | 普通输入、缓存读取、缓存写入、输出分别报价，按百万模拟 Token 计价 |
| 预算 | 每次请求设置上限；卖家最低要求采用最低预留金额，不是最低消费 |
| 失败与取消 | 卖家故障整单推理费为零；买家显式取消收已计量实际费用；剩余预算释放 |
| 资金 | DemoUSD 测试代币托管、受限消费授权、锁款、结算、超时自行回收、提款 |
| 内容与信任 | 内容不上链；平台和卖家可见请求；平台计量和判责，合约验证资金规则 |
| 仓库 | `onekb/Hackathon260905`，使用 SSH；公开发布范围按用户实际要求执行 |

首版不包含真实模型验证、TEE、投诉裁决、扣质押、完整订单簿、批量结算、桌面安装包、多模态和工具调用，也不承诺兼容所有 OpenAI SDK 行为。没有新增必须公开仓库、提供公网 Demo 或录屏的比赛要求。

## 验收要求

1. 两个独立卖家拥有不同钱包与报价；买家能指定或自动匹配卖家。
2. 网页和 API 发起请求，显示相同口径的账单与 Monad 测试网交易。
3. 已输出部分内容后卖家失败，整单推理费为零。
4. 显式取消只收取消生效前实际用量；例如预留 `1.00`、实际 `0.20`，释放 `0.80`。
5. 预算或输出上限触顶正常终止，费用不超过预算。
6. 缓存分类不重复计算输入，不跨买家、卖家或模型共享。
7. 幂等重试不重复锁款；并发请求不超出余额或授权。
8. 平台失联后，买家可在链上期限到达后自行回收并提款。
9. 全部界面和说明明确标识模拟推理、模拟计量与测试资产。

以上是验收目标，不表示全部已通过。分环境证据见 [进度](progress.md)。

## 决策记录

以下编号稳定保留。前序事件缺少精确时间，统一按 2026-09-05 的讨论顺序记录；不将缺失原题的编号回答还原成虚构问题。

### D01 — 黑客松保留独立节点，推理使用 Mock

- **背景：** 用户要求短时间交付，同时明确不考虑算力机房和客户端上游接入。
- **选择：** 卖家独立运行软件，提供可重复的模拟响应与故障模式；真实资金流程放在测试链上。
- **原因：** 可验证网络连接、预算与结算，不把真实模型接入放在关键路径。
- **后果：** Token、缓存和模型输出不能作为真实推理能力证明，界面必须标明 Mock。
- **依据：** 用户“输出的 AI 响应是 mock 的数据”“现在先不考虑”；[MVP 规格](../MVP_SPEC.md)。

### D02 — 网页与最小 API 同时提供

- **背景：** 用户尚未确定买家使用方式，随后选择同时有在线界面与最小 API。
- **选择：** 网页体验台、API Key 和文本聊天/SSE API 共用 Router。
- **原因：** 兼顾现场演示与开发者接入，避免两套计费逻辑。
- **后果：** API 只承诺已实现的文本聊天子集；网页仍需单独进行钱包及浏览器验收。
- **依据：** 用户“1.C 既要有在线 也要有最小 AP”；[MVP 规格](../MVP_SPEC.md)。

### D03 — 卖家主动长连接到中心 Router

- **背景：** 用户询问买家如何接卖家的 API，是否需要同步公网地址；接受平台承担链外处理。
- **选择：** 买家 HTTPS/SSE → Router；卖家主动 WSS → Router；钱包签名认证身份。
- **原因：** 卖家不需公网 IP、端口映射或部署公开 API，Router 能统一控制派单及预算。
- **后果：** 平台成为可见内容且受信的中介；生产入口需支持长连接。断线不重放订单。
- **依据：** 用户连接方式提问；[MVP 规格“连接与派单”](../MVP_SPEC.md)；[provider-hub.ts](../server/src/provider-hub.ts)。

### D04 — 按实际用量收费，四项报价与最低预留

- **背景：** 用户希望输入/输出分开报价，考虑缓存，单次预算由卖家设置最低要求；最初提出买家责任“100% 扣费”。
- **选择：** 四项报价；最低要求解释为最低预留；买家显式取消扣已产生的实际费用，剩余释放；卖家责任整单为零。
- **原因：** “买家责任”需要明确收费基数，不能自动等同于收满未消费预算。此解释已进入采用的 MVP 规格。
- **后果：** 取消前的输入和缓存用量也计费；网络断开不等同于显式取消；预算触顶属于正常结束。
- **依据：** 用户报价及责任要求、后续采用建议的回答；精确定义以 [MVP 规格“责任与终态”](../MVP_SPEC.md) 为准，不补造缺失的逐轮确认原文。

### D05 — 合约控制资金，Router 判定链外事实

- **背景：** 模型真实性和故障原因不能仅靠结算合约自动验证。
- **选择：** 合约保存报价快照、消费授权、预算和终态；Router 负责模拟用量和责任结果。每单设截止时间，买家到期可自行回收。
- **原因：** 把可以验证的资金约束放到链上，明确首版仍有哪些信任假设。
- **后果：** 不得宣传为无需信任的推理验证；恶意 Router 仍可能在授权范围内提交不真实的用量或责任。授权不包含提款权。
- **依据：** [MVP 资金边界](../MVP_SPEC.md)、[InferenceMarket.sol](../contracts/src/InferenceMarket.sol)。

### D06 — TEE、投诉和扣质押延后

- **背景：** 用户提出第二版可部署 TEE 或由另一功能裁量假模型并扣质押。
- **选择：** 保留为后续方向，首版不实现。
- **原因：** TEE 本身不等于证明上游模型身份；罚没需要请求绑定、可靠证据、裁决与申诉规则。
- **后果：** 回答风格和模型评分不能直接作为自动扣款依据；首版没有押金或罚没能力。
- **依据：** 用户的第二版建议、[MVP 第二版方向](../MVP_SPEC.md)。

### D07 — Monad 测试网与自建 DemoUSD

- **背景：** 用户确认必须部署 Monad 测试网，并希望 Web3 部分有助于比赛展示。
- **选择：** chain ID `10143`，自建六位精度 DemoUSD；展示报价、锁款、结算及超时回收。
- **原因：** 清楚区分测试资产和真实美元，避免把自建币称为官方 USDC。
- **后果：** Gas 使用测试 MON；失败免除的是推理费，已发生的 Gas 不会回退；必须保留真实交易证据。
- **依据：** 用户比赛要求回复；[部署记录](../contracts/deployments/inferpool-monad-testnet.json)。

### D08 — 使用 SSH 连接既有 GitHub 仓库

- **背景：** 用户提供 `onekb/Hackathon260905` 并要求“你用 ssh 的方式接吧”。
- **选择：** 初始化本地 `main`，设置 `git@github.com:onekb/Hackathon260905.git` 作为 origin。
- **原因：** 沿用用户指定仓库和现有 SSH 认证。
- **后果：** 成功连接不等于代码已提交或推送；公开发布状态单独记录。
- **依据：** 用户仓库/SSH 消息；本次检查的 `git remote -v` 与 `git status`。

### D09 — 钱包授权由用户完成，后台常规配置由 agent 执行

- **背景：** 测试网签名需要 Alchemy session，买家钱包需要 Para；用户完成登录后不熟悉组织创建操作。
- **选择：** Router 使用已授权 Alchemy session；用户明确授权 agent 代操作 Para 后，创建 InferPool FREE 组织与项目、配置前端公开 Key。
- **原因：** 复用已授权身份，避免收集私钥；让用户只处理必须由本人完成的认证步骤。
- **后果：** 登录或配置完成不代表买家钱包交易验收通过；签名会话过期需重新认证。Para 私密 Key 不进入项目文档。
- **依据：** 用户“我已授权”、Para 登录完成回复、“你能帮我操作吗”；当前任务的后台操作结果。前端 SDK 方案见 D11，验证状态见进度。

### D10 — 文档随开发和后续对话持续更新

- **背景：** 用户担心后续无法了解完整项目始末。
- **选择：** 专职文档 agent 维护 `docs/`，根 `AGENTS.md` 约束每轮实质变化同步主题文档、进度与对话日志。
- **原因：** 将决定、实现、证据和未决事项分开保存，方便后续接手。
- **后果：** 主 agent 每次里程碑需主动同步，不能仅依赖子 agent 记忆；不创建定时任务，不记录凭证或原样复制聊天。
- **依据：** 用户“要一边写，一边完善文档……包括后面的对话，也是要同步完善文档的”。

### D11 — Para Lite 邮箱内嵌钱包与真实本地签名器

- **背景：** 用户没有要求外部钱包；full SDK 引入与当前 EVM 场景无关的多链依赖，首次审计有待处理项。
- **选择：** 使用 Para 3.18 Lite、`react-core/evm/viem` 与 `viem-v2-integration` 的邮箱内嵌 EVM 路径，暂不加载外部钱包连接器或 WalletConnect。
- **原因：** 减少依赖和新增注册项；保留完成本次钱包认证与测试网资金操作所需能力。
- **后果：** 首版入口为邮箱内嵌钱包。交易须保留 Para 提供的真实 `LocalAccount`，不能用地址字符串替换。轻量路径要重新完成审计和交互验证；CLI doctor 对该路径的静态误报不能当作已验收或阻止独立检查的依据。
- **依据：** 当前实现决策、[para-wallet.tsx](../web/components/para-wallet.tsx) 与本机 CLI/SDK 源码检查；最终结果见 [进度](progress.md)。

### D12 — 第二卖家先隔离会话，再核对钱包身份

- **背景：** Router 与已有卖家使用同一 Alchemy session；直接在原 CLI 配置重连会撤销旧 session，影响正在使用的签名能力。
- **选择：** 保留 Router 当前会话；如以后增加第二卖家，只给其进程使用位于不同父目录的 `ALCHEMY_CONFIG` 配置文件路径，由用户在 Dashboard 批准目标钱包，再读取不同地址验证。当前先推进 Para 独立买家流程。
- **原因：** `--instance-name` 只是标签；CLI 无钱包 ID 选择器，配置目录独立也不能证明第二 EOA。身份必须以实际地址和签名认证为准。
- **后果：** 不使用原配置 `--force` 来“增加卖家”；没有新钱包或第二卖家完成声明。买家地址不同于卖家只证明买卖身份分离，不构成双卖家市场验收。
- **依据：** 本轮对 Alchemy CLI 0.24.0 的只读源码检查与 [官方 CLI 说明](https://www.alchemy.com/docs/alchemy-cli#wallets-and-signing)；具体函数和文件位置见 [运行手册](runbook.md#增加第二卖家时保留-router-会话)。没有执行会话切换或新增交易。
